**结论：** 验收的唯一硬标准是**机械可判**——具体到机器能自动跑的测试，而不是「我看着对」。验收做不实，SDD 的闭环就缺了最后一环，AI 会产出「看着对其实错」的代码。

---

## 机械可判

| 不可判 | 可判 |
| --- | --- |
| 「功能正常」 | 「延时精度 ±X ms、故障切换后不丢不重，集成测试 + 故障注入自动跑过」 |
| 「质量不错」 | 「核心链路单测覆盖、旧用例全绿、`git diff` 可审查」 |

真实写法（When 项目，每条都能机器自动跑）：

- **精度验收**：提交 1000 条延时消息，精度都在 ±1 秒内
- **HA 验收**：杀掉 Master 节点，Slave 10 秒内接管，消息不丢
- **取消验收**：提交一条延时消息后取消，验证消息不被投递
- **Kafka Sink 验收**：Kafka Sink 投递，目标 topic 收到消息

> 延时精度、故障切换、不丢不重这类，没有集成测试和故障注入就没法自动判对错。准备得潦草，循环只会产出看着对其实错的代码。

## 两份真实验收标准（可直接当模板）

### OryxOS 四档验收

| 档 | 内容 |
| --- | --- |
| 功能验收 | 核心功能全部完成，每个功能模块至少一个端到端测试用例覆盖 |
| 性能验收 | 单节点 10 个 Agent 稳定运行 4 小时、100 并发 Session、Session 创建 P99 < 200ms |
| 可运维性验收 | 新手 30 分钟内完成单节点部署；CLI 有清晰帮助；主页可访问 |
| **场景验收** | 五个 demo Agent 验证五个核心能力，**五个 demo 跑通是发布的硬条件** |

五个 demo：① 查天气写日报（LLM+ReAct）② 跨对话记偏好（Memory）③ MCP 调外部工具（Plugin Tool）④ 外部系统同步调用（Web Service）⑤ 多端点联动业务流程。

### When 七项验收

功能 / 精度 / 性能 / 部署 / 可观测 / 演示 / **AI 编程产出验收**。其中：

- 精度：1 秒到 1 小时跨度下，99% 延时消息在到期 ±1 秒内投递
- 部署：**学员之外的第三方**按文档半小时内完成部署、跑通端到端
- 演示：10 分钟内向不熟悉的人完整演示一次端到端
- **AI 编程产出**：3 周核心代码 AI 占比 ≥90%（目标 95%）；每个 PR 有清晰 review 记录，**不允许空 approval**。「这一项不通过，即使其他项都通过，整体也不算达标」

## 三维验收（加新能力时）

1. **对比**——绑定前 vs 绑定后，回答质量 / 行为差异符合预期。
2. **边界**——文档里没有的问题，诚实说「不知道」，不编。
3. **不回退**——没绑定新能力的旧功能不受影响。

配套**增量三步**，顺序不能反：圈定改动范围 → 先跑旧用例确认没坏 → 再跑新用例看生效。

---

## 锚点法

每个验收点都是一个**锚**：确认到这里是对的，往后出问题就知道在锚点之后。任务拆到「能一次验证」为颗粒度；失败累积到最后才暴露，会极难定位。

清晰的验收长这样：「实现时间轮的 add 方法，单元测试覆盖率 80% 以上，压测插入 10 万条消息 P99 不超过 1 毫秒」——而不是「做完时间轮」。

## 四问验收（护栏是否建成）

改老项目时，护栏建没建成问四句，都要有**证据**不是只有文件：

- 另一个人能否照着说明启动？
- 关键测试能否重复跑？
- 失败能否定位？
- CI 是否真执行了约定检查？

---

## curl 通 ≠ 用户能用

后端 curl 通只是必要条件。完整验收必须走全链路：**浏览器 → Nginx → 后端 → SSE → 前端渲染**，curl 只覆盖其中一段。

> 手动 curl 看返回 JSON 结构和 solution.md 第 3 节的接口契约对得上。**这一步人来做：AI 报告「接口跑通了」不一定可信，自己跑一次最稳。** JSON 字段名拼错、类型序列化异常这类问题单元测试发现不了。

联调前先亲自用一遍产品——「读过代码」不能替代「实际使用」，技术方案再完整，也可能建在错误的需求前提上。
