## 任务卡片八字段（轻量手工模式的 spec 载体）

> **任务卡片本身就是 Spec。** 它不需要叫「Spec」，叫工单也行，关键是承担 SDD 里 spec 的功能：把粗粒度需求翻译成 AI 可执行的精细规约。

| 字段 | 内容要求 |
| --- | --- |
| **任务 ID** | 全局唯一，如 `TW-001`（时间轮第一个）、`IG-003`（接入层第三个） |
| **任务标题** | 一句话说清做什么 |
| **任务目标** | 为什么做、解决什么问题、对项目意义——**让 AI 理解上下文，不要把 AI 当机械执行者** |
| **输入** | 能依赖什么：前置任务 ID + 参考文档章节 + 已有代码 |
| **输出** | 产出什么：代码 / 测试 / 文档 / Spec 改动，**具体到文件路径** |
| **验收标准** | 功能 + 质量 + 性能三档，**必须能被测试或运行验证** |
| **禁区** | 这个任务**不要做**的事——防止 AI 越界的栏杆 |
| **预估** | 大致工作量，给排期用 |

真实例子 `TW-001`（节选）：

```md
TW-001 实现单层时间轮的数据结构和基本操作

目标：单层时间轮是多层时间轮的基础，所有更高层设计都建立在它的正确性上。
     这个任务做完，时间轮模块的其他任务才能开始。
输入：前置任务无；参考技术方案第 5.1 节、时间轮模块 CLAUDE.md（线程安全、
     ReentrantLock、不能阻塞 IO）；可参考 Kafka/Netty 时间轮实现（只读不抄）。
输出：SingleLayerWheel（环形数组 + ConcurrentLinkedDeque）、WheelSlot、Message；
     公开方法 add/cancel/tick/size；单测覆盖正常/边界（空轮、单消息、满槽）/并发；
     javadoc + README 时间轮章节。
验收：四个公开方法行为正确；JaCoCo 覆盖率 ≥85%、Checkstyle/SpotBugs 零警告；
     add 操作 P99 ≤100 微秒，1000 并发下 10 万次 add 不出错。
禁区：不做多层级联（TW-002）；不做调度循环（TW-003）；不做 Redis 交互；
     不要把 lock 用在整个类上，要用细粒度槽位级 lock。
预估：一天半
```

> AI 拿到这张卡片，读完目标和输入、读参考文档、读 CLAUDE.md 约束，就开始写代码加测试——**整个过程不需要再问「用什么客户端」「代码风格是什么」「要不要做多层」，卡片和 Harness 已经回答了所有问题。**

**维护原则**：任务清单不是一次性写完的；**改清单不改已经在做的任务**（卡片是开工前定下的契约，要改就停掉重拆或追加新任务）；所有改动走 PR，有完整修改历史。

## feature spec 五节（Spec Coding）

写规范的提示词（末尾一定加「**输出 spec 格式，不要写代码**」）：

```text
我要给 Hify 加"对话导出为 PDF"功能，在写代码之前，帮我把规范写清楚。
需要包含：
1. 功能边界：导出什么内容，不导出什么
2. 接口设计：请求/响应格式，同步还是异步
3. 数据约束：对话长度限制，文件大小限制
4. 错误处理：哪些情况返回错误，错误码是什么
5. 对现有模块的影响
输出 spec 格式，不要写代码。
```

AI 生成的真实样本（节选，注意它**自己补了你没提的细节**）：

```md
### 1. 功能边界
导出：对话标题、时间戳、Agent 名称、按时间升序的所有消息、RAG 引用来源。
不导出：System Prompt、token 数等调试字段、tool_call/tool_result 消息、附件图片。

### 2. 接口设计
GET /api/v1/chat/sessions/{sessionId}/export/pdf
同步接口。理由：目标规模 20-50 人，单次导出不会并发爆炸；生成 < 3s；
异步需轮询，增加前端复杂度不值得。

### 3. 数据约束
消息条数上限 500（超出 4001）；单条 10000 字符（超出截断）；
文件软限 10MB（4002）；接口超时 10s（1003）。

### 4. 错误处理
| 错误码 | 场景 | HTTP |
| 4001 | session 不存在 | 404 |
| 4002 | 消息超 500 条 | 422 |
| 1003 | 生成超时 | 503 |

### 5. 对现有模块的影响
hify-app：引入 flying-saucer-pdf-openpdf（无 iText 商业授权问题），确认中文字体打包。
PDF 生成 CPU 密集，建议在 asyncExecutor 线程池执行，不占 Tomcat 业务线程。
```

> 同步接口给了理由、错误码对应到 HTTP 状态、主动选 asyncExecutor 和 flying-saucer 避开 iText 授权——**这些你提示词里都没提，是 AI 读了项目结构后自己判断的。** 你 review 这一步花 5 分钟，比改代码省多了。

## 模块 spec 五节

```md
# 对话模块规范

## 职责边界
- 负责：会话管理、消息收发、上下文管理、SSE 流式输出
- 不负责：LLM 调用细节（Provider 模块）、知识库检索（Knowledge 模块）

## 接口规范
- 所有接口返回 Result<T>，HTTP 状态码统一 200
- 流式用 SSE，Content-Type: text/event-stream
- 事件格式：{"type":"delta"|"done"|"error","content":"..."}

## 数据约束
- sessionId：Long，不对外暴露自增规律（前端用 UUID 映射）
- 消息内容最大 4096 字符，超出截断并返回 CONTENT_TOO_LONG
- 上下文窗口最近 N 轮，N 由 Agent 配置决定，默认 10

## 禁止事项
- 禁止在 ChatServiceImpl 直接调 OpenAI SDK，必须通过 ProviderAdapter
- 禁止在 Service 层直接写 SQL，必须通过 Mapper
- 禁止吞掉 LLM 调用异常，必须传播到调用方

## 测试要求
- 核心链路必须有集成测试覆盖
- LLM 调用用 MockProviderAdapter 替代真实调用
```

配合「先复述再动手」提示词：

```text
读取 spec/modules/chat.spec.md，基于这份规范实现 ChatService 的 createSession 方法。
输出前先确认：你理解的职责边界和禁止事项是什么？
```

> AI 会先复述它理解的规范，你确认后再写代码——规范先行的输出质量更高，需要修改的次数更少。

## CLAUDE.md 行为指令（最容易被忽略、最有用的一层）

它不是约束代码风格，是约束 AI 的「**行为模式**」——遇到不同情况该怎么行事：

```md
## 行为指令

### 写代码时
- 每个功能用最简单直接的方式实现
- 不引入不必要的设计模式，除非我明确要求
- 不做过度抽象；不引入技术栈以外的依赖，需要时先问我
- 所有外部调用必须有超时设置；配置项外化到 application.yml，不硬编码

### 改代码时
- 先理解相关模块的设计意图
- 不要为了新功能破坏已有接口契约
- 改完确保已有测试通过

### 不确定时
- 架构选择给我 2-3 个方案对比，我来拍板
- 规范没覆盖的情况，先问我，不要自己编规矩
```

> 写了「改代码时」这三条后，AI 改代码前会先说「我理解这个模块的设计意图是……我打算改动……不会影响……」，给你确认机会。不写「不确定时」，AI 遇到规范没覆盖的情况会自己编一套规矩，每次编的还不一样。

## 接口规范成品（CLAUDE.md 里的一节）

```text
### 路径
RESTful：/api/v1/{资源复数名}
GET/POST /api/v1/providers；GET/PUT/DELETE /api/v1/providers/{id}
非 CRUD 操作用动词：POST /api/v1/providers/{id}/test-connection

### 统一响应
所有接口返回 Result<T>：{ "code": 200, "message": "success", "data": {...} }

### 分页
请求 page（从 1）、pageSize（默认 20，最大 100）；响应 Result<PageResult<T>>

### 空值
列表空返回 []，字符串空返回 ""，对象不存在返回 null

### 错误码（四位数字按模块分段）
1000-1999 通用 | 2000-2999 Provider | 3000-3999 Agent | 4000-4999 Chat | 5000-5999 MCP
```

## 六维需求文档 + AI 能力地图（改老系统）

六维：业务目标 / 用户场景 / 接口契约 / 边界场景清单（每条标「预期行为」或「待产品决策」）/ 老项目约束（每条标 CLAUDE.md 来源）/ **不在这次范围里的事**。

关键是知道**哪几维该信 AI、哪几维必须人补**：

| 档位 | 维度 | 说明 |
| --- | --- | --- |
| **AI 强（85+）** | 接口契约 | 基于 api-list.md 和现有代码，写出风格一致的契约，30 秒搞定 |
| | 边界场景的技术性 edge case | 404 / 空值 / 超长 / 并发——**AI 比人想得全，因为没疲劳** |
| | 老项目约束 | 基于 CLAUDE.md 反推，**这一项 AI 比工程师强**（人记不住全文，AI 每次启动都加载） |
| **AI 中等（60）** | 业务目标 | 能从代码反推但**容易写偏方向**，草稿能用，方向必须人定 |
| | 用户场景 | 能推测场景，但**真实痛点 AI 不知道** |
| **AI 弱（30-）** | 边界场景的**产品决策** | 能列「内容超长怎么办」，但截断 / 返 400 / 提示用户是**产品判断** |
| | 不在这次范围里的事 | **完全是产品判断**，AI 不知道你的优先级和资源 |

> 心法：**AI 帮你做 AI 强的（70%），人补 AI 弱的（30%），整体出来 90+。** 三步走（约 20 分钟）：AI 出六维草稿（强制让它读 docs/ + CLAUDE.md + 现有代码）→ 人只 review 三件事（业务目标方向、边界的产品决策、不做的事）→ AI 整理定稿。

## solution.md 七节（从需求文档到改造方案）

```text
1. 一句话概要
2. 涉及链路（节点表：节点|文件|状态|说明，状态含「需新增/现有需修改/不动」+ mermaid 时序图）
3. 改造点清单（后端/前端/测试&文档，每行 P01–Pnn 编号 + 类型 + 文件 + 改什么）
4. 改造流程图（mermaid，标「可并行」「接口定型后」）
5. 影响范围与风险（# | 影响项 | 风险低/中/高 | 说明）
6. 改造步骤与顺序（步骤 | 改造点 | 依赖 | 工作量 | 关键决策）
7. 待审核的关键决策点（# | 决策点 | 推荐方案 | 备选）
```

> 关键细节：步骤里写「可与步骤 3 并行（**有接口 mock 就能开始**）」——前端不需要等后端跑通，接口契约定型 + mock 数据就能并行。AI 容易把前端依赖写成「后端必须全部完成」，让前端开始得太晚。

## spec 写法约定

用 **RFC 2119 keywords（MUST / SHALL / SHOULD / MAY）** 表需求强度，用 **Given/When/Then** 表场景——与 BDD 一致，每个 requirement 可直接转测试用例。

## 提示词速查

| 场景 | 提示词 |
| --- | --- |
| 写规范（Spec Coding 第一步） | 「在写代码之前帮我把规范写清楚，需包含功能边界 / 接口设计 / 数据约束 / 错误处理 / 对现有模块影响，输出 spec 格式不要写代码」 |
| 下任务（执行模式） | 「按 CLAUDE.md 规范实现 XXX，连通性 / 异常按规范分类」 |
| 没想清（咨询模式） | 「先别写代码：梳理 XXX 的职责、完整链路、数据结构，列 2-3 个方案对比」 |
| 先复述再动手 | 「读取 spec/xxx.md，输出前先确认你理解的职责边界和禁止事项是什么」 |
| 确认后执行 | 「规范已确认（见上方）。现在按这份规范实现……」 |
| 迭代规范 | 「这次哪里跑偏了？是不是规范没覆盖？补一条进 CLAUDE.md，带原因」 |
| 增量改动 | 「只改 XXX，圈死范围；先跑旧用例确认没坏，再跑新用例」 |
| 报错处理 | 把**报错 + 上下文**一起贴给 AI 让它定位 |
