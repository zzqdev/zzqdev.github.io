**结论：** SDD（Spec-Driven Development）= 在 AI 生成代码之前先生成规格（spec），让 spec 成为项目的事实来源、AI 与人的契约。代码变成 spec 的「编译产物」——你改规约，让 AI 重新生成，而不是去手改代码。

> 译名提示：Robert 全链路课译作「**规范**驱动开发」，实战营资料译作「**规约 / 规格**」，本系列统称 SDD，三者同义。

---

## 四种角度的定义

| 来源 | 一句话 |
| --- | --- |
| Robert 02 讲（最朴素） | 先定规范，再让 AI 按规范执行，而不是直接让它写代码 |
| 实战营 03-07（最本质） | 把「想清楚自己要什么」工程化；spec 是有结构、有验收、有边界的可执行规格 |
| 实战营 03-10（最工程化） | spec 是项目的事实来源，不是 chat 历史 |
| 实战营 03-19（最凝练） | 让 spec 成为代码行为的契约和单一事实来源，把 AI 从「代码生成器」变成「按规格干活的协作者」 |

SDD 的灵魂：把「想」从藏在你脑子里的**隐性知识**，变成可审查、可共享、可被 AI 消化的**显性产物**。

---

## 为什么不靠「写好 Prompt」

| | 写 Prompt | SDD |
| --- | --- | --- |
| 性质 | 一次性技巧 | 贯穿项目生命周期的方法论 |
| 作用范围 | 这一次对话 | 整个项目、所有人 / 所有 Agent |
| 跑偏时 | 再调一次提示词 | 问「规范没覆盖到？」补一条 |
| 沉淀 | 散在聊天记录 | 落在 CLAUDE.md / 规格文件，跟代码一起版本管理 |

根因：**Claude Code 没有长期记忆。你上一轮给的规范，这一轮它根本没看到——不是「忘了」，是「没看到」。** AI 是放大器不是发动机：你有方向它放大十倍，没方向放大的是零。

---

## SDD vs 已有概念（「不是什么」）

| 对比 | 关键差异 |
| --- | --- |
| 传统瀑布 | 瀑布 spec 是死的、给人看的；SDD spec 是活的、**给 AI 看的**（spec 就是 AI 的 system prompt，更新 spec 等于更新 AI 的工作上下文） |
| vibe coding | vibe 需求易失（绑定会话）；SDD 需求持久（绑定仓库、版本管理） |
| Cursor Rules / AGENTS.md / CLAUDE.md | 那些是静态 context，**不约束工作流**；SDD 强制阶段化（specify→plan→implement 不能跳） |
| TDD | **TDD 是单元层面的 SDD**，一个失败的测试就是一个微型规约 |

三维度对照（实战营 03-04）：

| 维度 | 传统方法论 | SDD |
| --- | --- | --- |
| 规格用途 | 用于沟通 | 用于执行 |
| 真理来源 | 代码是真理 | 规格是真理 |
| 生成方向 | 规格落后于代码 | 规格领先于代码 |

## vibe coding 的四个硬问题（SDD 要解决什么）

「给 AI 一段模糊需求让它直接生成代码」，在中小任务上不明显，中大规模项目上暴露四个硬问题：

1. **需求漂移**——跨会话时 AI 每次重新理解背景，前面的决策被遗忘
2. **架构失控**——AI 倾向生成「看起来能跑」的代码，多次迭代后变成一团乱麻
3. **回退困难**——没有正式需求文档，做错了不知道回到哪个状态
4. **无法协作**——多人提示词理解不一，产出风格不一致

翻车案例（Robert 02 讲）：同一项目里 Provider 模块和 Agent 模块，因为下任务时规范没带进来，生成出两种风格——

```java
// Provider：实体不加后缀、返回 Result<T>、错误码 1000 段、直接 new
// Agent：  AgentConfig.java、ResponseEntity、错误码撞号 1001、Builder 模式
```

每条单独看都不是 bug，功能都正常；放一个项目里就是两种风格。SDD 就是把规范固化进 CLAUDE.md，让每次任务都自动带上。

## 在三大支柱里的位置

| 支柱 | 管什么 | 一句话 |
| --- | --- | --- |
| **SDD** | 目标（target） | 做什么——把需求变成规范 |
| **Harness** | 边界（boundary） | 允许在什么边界里做——护栏、约束、可执行验收 |
| **Loop** | 执行（loop） | 怎么在圈里自己转——AI 自主跑、人在关键点纠偏 |

注：实战营认知篇讲「SDD + Harness **两大**支柱」，课程导论与后续补上 **Loop Engine** 成「**三大**支柱」。

**SDD 告诉 AI 做什么，Harness 保证 AI 做对**；前者从需求侧约束，后者从执行侧约束。没有 Harness 的 SDD，是有清晰目标但没有控制力；没有 SDD 的 Harness，是有强控制力但没有清晰目标。「验收要机械可判」（→ [05](/ai/sdd/05-acceptance/)）其实是 Harness 的活儿。

---

## 底层假设（最深刻的一条）

**AI 不是被信任的，是被工程化使用的。** 它是能力极强但缺判断边界的执行者，需要被精确指挥、严格约束、持续校验。接受这个假设，SDD 和 Harness 都是自然产物；抗拒 SDD，本质上是抗拒这个假设。模型升级补不上「商业判断、团队约束、产品方向、关键拍板」——这些根本不属于模型能力范畴。

---

## 建系统与改系统都适用

- **从 0 建系统**（全链路开发）：动第一行代码前，把产品边界、技术选型、运维预期写进 CLAUDE.md；规范先于代码。
- **改老系统**（老项目改造）：把「一句话需求」翻成需求文档（六维：业务目标 / 用户场景 / 接口契约 / 边界场景 / 老项目约束 / **不做的事**），再翻成「改哪里、影响哪、按什么顺序」。

两端共用同一套 SDD / CLAUDE.md / 三层分工，区别只在规格的起点是「白纸」还是「存量」。
