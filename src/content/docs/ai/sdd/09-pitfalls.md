**结论：** SDD 不是银弹。这一篇收集课程里对 SDD 的「冷水」和真实事故，外加一份分类踩坑清单——**谁要是告诉你 SDD 已经是确定答案，他在卖东西。**

---

## 冷水一：SDD 还远不成熟

> **Thoughtworks 技术雷达 2026 年初把 SDD 放在「评估」（Assess）这一环**：值得关注，但附了严厉警告——**工作流仍然繁琐、过于意见化**。更根本的是，截至 2026 年初，**业界连「规约到底是什么」都还没有共识**：Spec-Kit、AWS Kiro、OpenSpec、Tessl、Google Antigravity 各做各的，互相借鉴又互不相同。

正面的一面（同一篇）：**规约正在成为主产物**——「代码之于规约，就像编译产物之于源代码。你不会去手改二进制，你改源代码再重新编译。SDD 想做的，是让代码变成那个『没人手改的编译产物』」。而且「用规约驱动实现」软件工程界做了几十年——**TDD 就是单元层面的 SDD**，过去规约的载体是测试用例、类型签名、接口契约，AI 时代只是把它推到显式、中心化、机器可读。

---

## 冷水二：「写好 SDD 扔给 AI 跑一晚上」做不到

> 很多新闻说：写好 SDD 直接扔给 AI，它跑一晚上就把整个项目搞定了。**个人体感：做不到，至少现在做不到。**

不是 AI 能力不够，是这句话偷换了概念：**保证代码质量的不是 AI，是体系。AI 只是体系的执行者。**

- 「AI 帮你保证质量」（不现实）= 你把代码交给 AI，它自动发现所有问题、自动写对测试、自动保证稳定。AI 写代码时专注功能实现，不会主动质疑自己的安全模型，不会想到权限校验漏洞，不会考虑并发一致性。
- 「体系保证质量，AI 协助执行」（现实）= 你先建质量体系——**识别核心链路、划定测试边界、制定 review 策略**——再让 AI 在体系里高效执行。体系是你建的。

---

## 冷水三：老项目本来就没有清晰的 spec

老项目改造课**刻意不专门讲 SDD**：

> 老项目本来就没有清晰的 spec，**你强行给一段老代码「补 spec」意义不大**。而且 SDD 的核心思想（先约束、再动手）已经在三层控制里了，不需要再给它一个流程化的壳。Spec-Kit、Kiro 这些工具**不用**——不是不好，是跟老项目改造的主线不对路。

老项目走的是另一条路：六维需求文档 + 两次翻译（design.md → solution.md）+ 先补安全网（Characterization Test）再改造（→ [07](/ai/sdd/07-templates/)）。**工具不是学得越多越好，是够用就停**——每学一个新工具认知成本就上去一点，注意力被工具切碎，真正花在项目上的思考反而少了。

## 冷水四：SDD 忽略全链路影响面的真实事故

> 一位学员让 AI 按 SDD 设计存量系统一个老功能的链路迭代，代码完成并上线。线上**用户端 7 秒拿不到结果——爆雷了**。原因：**AI 不知道这条链路上的改动会影响哪些下游服务，也不知道端用户的体验 SLA。代码本身没 bug，但全链路影响面被忽略了。**

本质：**不是 AI 写错了代码，而是 AI 没有被赋予「在设计阶段审视影响面」的职责和上下文。** 解法是配一个 `impact-analyzer` 只读子代理（追调用链 + 交叉引用链路拓扑/SLA → 输出影响面报告，配置见 [08](/ai/sdd/08-practice/#进阶给-ai-配一个影响面分析只读子代理)）。

## 踩坑清单（分类速查）

**写规范**

- [ ] 不具体 → AI 还要「猜」就等于没写（判断标准：AI 看到后是否还需要猜）
- [ ] 贪多 → 上下文窗口有限，塞太多反而稀释重要的几条；CLAUDE.md 超 200~300 行就是信号
- [ ] 只写规则不写原因 → 涉及工程权衡的规范必须加「为什么」（全量删除 vs 差异比对案例）
- [ ] 想一次写完 → **规范是长出来的**，跑偏一次补一条
- [ ] 把任务流程塞进 CLAUDE.md → 全局规范放 CLAUDE.md，任务流程放 Skills
- [ ] 老项目 CLAUDE.md 写成 docs/ 的复制粘贴 → 应该是**索引 + 常识**，禁区和历史包袱必须手写

**用工具**

- [ ] 喂给 Spec-Kit 的文档不是最新版 → plan 会按错误的模块结构拆分
- [ ] 跳过 `/speckit.analyze` → spec 跟代码漂移，必须作为每个 user story 结束的硬性环节
- [ ] Spec-Kit 不锁版本 → 命令名 / artifact 格式 / 集成方式在版本间会变
- [ ] 乱用 community extension → Spec-Kit 有 70+ 社区扩展，主体开发期只用官方核心命令
- [ ] 小增量硬上 Spec-Kit → 800 行 spec 对小改动是 overkill，流程开销大于任务本身
- [ ] 大型 brownfield 硬上 Spec-Kit → 十万级文件超出 LLM context limit
- [ ] Superpowers 的 `writing-specs` 和 Spec-Kit 重复 → 选一个用

**执行过程**

- [ ] **两轮推断叠加**：自动化模式拆任务 80% × 执行 80% = 64%，误差**相乘**不是相加
- [ ] 任务粒度偏大 → AI 在大任务里更容易凑合、跳过、幻觉；**AI 不理解时不会停下来问，会编造一个看似合理的实现**
- [ ] 跨 task 上下文断裂 → 定期让 AI 重读 spec.md + plan.md + 最近代码
- [ ] AI 跑偏 constitution → 把「AI 最容易写错的点」显式写进 task 注意事项
- [ ] 任务做着做着改任务卡片 → 卡片是开工前的契约，要改就停掉重拆或追加新任务
- [ ] AI 写完人重写一遍 → 等于人在写代码，要回头优化 Spec / CLAUDE.md 而不是绕过 AI
- [ ] 人手写超过 10% → 回头查：Spec 不清晰？CLAUDE.md 缺信息？任务粒度太大？
- [ ] 空 approval → review 放水等于跳过训练，**这条比「AI 写 90%」更重要**
- [ ] 老项目先重构再补测试 → 顺序反了，**必须先写集成测试锁住现有行为**（老项目的「bug」可能被下游依赖）

**心态**

- [ ] 第一次用 SDD 会觉得别扭（「直接写代码不就行了」）→ 所有从手撸切过来的人都经历过，撑过第一次就有正反馈
- [ ] 追工具不追问题 → 「觉得需要新工具时，先问：是现有工具解决不了，还是用得不够好？」90% 的质量问题是 CLAUDE.md 写得不够清晰
- [ ] 迷信 SDD 已成熟 → 见冷水一
- [ ] 轻量手工模式下工具过载 → Subagents 反而是负担，Hooks 是可选（你这个「人 review」本身就是反馈循环）

## 资料存疑处（写博客/落地前请核实）

课程资料对若干事实表述不一致，落地前建议以官方仓库核实：

- **译名**：Robert 全链路课用「**规范**驱动开发」，实战营用「**规约 / 规格**」，本系列统称 SDD。
- **Spec-Kit 安装**：Robert 31 讲写 `npm install -g spec-kit` + `spec/` 目录（示意性）；实战营写 **Specify CLI（Python，`specify init`）+ `.specify/` 工作区**（与 GitHub 官方一致）。以后者为准。
- **命令前缀**：`/speckit.constitution` 带前缀 vs `/specify` 无前缀两种写法都有；Claude Code 集成已从 slash 命令演进到 **skills 模式**。
- **核心命令数**：有「四个命令」与「6 核心 + 3 可选」两种说法。
- **支柱数**：认知篇讲「SDD + Harness **两大**支柱」，课程导论与后续补 Loop Engine 成「**三大**支柱」。
