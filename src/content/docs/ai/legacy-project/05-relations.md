局部看清零件之后，真正容易踩坑的是关系：  
**两个都对的东西，拼错了，照样翻车。**

这一篇不介绍新名词，只画依赖和边界。


## 1. 这一篇要回答什么

我想能回答三种问题：

- 这两个东西是互补、替代，还是各管一段？  
- 这个场景该让哪几层同时上场？  
- 文档写了一堆，为什么执行还是飘？

关系篇的完成感，是「地图上的线」，不是又多记几个工具名。

---

## 2. SDD 和 Harness 如何合成闭环

最短的关系式：

> SDD 告诉 AI 做什么；Harness 保证 AI 做对。

SDD 从需求侧约束：目标、边界、验收。  
Harness 从执行侧约束：规则、工具箱、权限、钩子、先规划。

缺一边的症状很典型：

- 有 SDD 无 Harness：Spec 很美，执行改错目录、跳过测试、不可逆操作已经发生  
- 有 Harness 无 SDD：拦得住胡来，但「做对了你其实不想要的东西」拦不住  

共享假设也很重要：**AI 是被工程化使用的执行者，不是被无条件信任的同事。** 不接受这句，两套东西都会显得繁琐；接受了，它们是自然产物。

---

## 3. Spec-Kit、OpenSpec、Superpowers 的边界与可否组合

三者不在同一维度上硬刚：

| 东西 | 主要位置 | 关系 |
| --- | --- | --- |
| Spec-Kit | SDD 工具 / 完整规格流 | 与 OpenSpec 是流派差异 |
| OpenSpec | SDD 工具 / 增量规格流 | 改造场景常更顺 |
| Superpowers | Skills 编排 / 工作流框架 | 可挂在任一 SDD 姿态下 |

可以组合：例如 OpenSpec 写 delta，执行期用一套工作流型 Skills；或 Spec-Kit 产出 tasks，落地时用 CLAUDE.md + Hooks 当 Harness。  
不建议的是：**同一需求并行两套真相来源**——两份 Spec 打架，比没有 Spec 更糟。

---

## 4. Skills 与 MCP、Subagents、Commands、Plugins 的关系

一张关系草图：

```
MCP ──────── 提供「能调用的外部能力」
Skills ───── 规定「某类任务怎么做」（可调用 MCP / 本地工具）
Commands ─── 人手动触发的短流程（轻量 Skill）
Subagents ── 隔离上下文的执行单元（可被 Skill/任务调用）
Plugins ──── 打包与分发的容器
```

常见误读：把 MCP 当 Skill，或把 Subagent 当「更强的 Skill」。  
能力入口、流程标准、上下文隔离，是三件不同的事。混用名词，配置时就会装错层。

---

## 5. Agent vs LLM / Chatbot / Workflow 的界限

继续用五组件当尺子：

- **LLM**：只有决策引擎原料  
- **Chatbot**：LLM + 一点对话记忆，Tools / Loop 弱  
- **Workflow**：Tools + Loop 强，决策写死，缺自主  
- **Agent**：五件相对齐全，能在环境里闭环  

界限划清，是为了预期管理：别拿 Chatbot 的交互期待 Agent 的交付；也别把死流程自动化吹成「智能体革命」。

## 6. 工具七层如何配合：写新模块、改老项目、接 CI/CD

层不是按顺序点菜，是场景里同时上场。

**写新模块**：方法论（SDD）→ Spec 工具 → CLAUDE.md → Plan Mode → Claude Code / IDE → Hooks 收尾。  
**改老项目**：Subagents 分读 → delta spec → Permission 锁目录 → Hooks 保回归；工具层反而不是主角。  
**接 CI/CD**：工作流层（Actions + `claude -p`）串起配置、协议（gh）、模型；人从操作者变成设计者。

同一把七层尺，三种场景重心不同——这就是「关系」比「清单」值钱的地方。

---

## 7. 项目文档链：调研 → 需求 → 技术方案 → AI 实施指引

课前项目篇（OryxOS、When）几乎都按同一条链铺：

1. **业界调研**：问题空间、竞品、术语  
2. **需求文档**：做什么、不为谁做、验收  
3. **技术方案**：怎么做、关键决策、风险  
4. **AI 编程实施指引**：人 + AI 怎么在这个项目里落地（Harness、路径选择、禁区）

对人读，这是项目预习；对 AI 协作，这是「想」的上游水库。  
缺第 4 环的项目很常见：方案很帅，一跟 Agent 开工就失忆——因为没人把方案翻译成 AI 吃得下的约束与节奏。

OryxOS 偏复杂系统 / Spec-Kit 混合；When 偏分布式组件 / 轻量手工——**文档链同构，落地姿态不同。**

---

## 8. 「想」的产物如何喂给「做」的护栏

理想的咬合是管道，不是两堆文件：

- Spec / 需求 / 方案 → 写入或引用进 CLAUDE.md、Plan、tasks  
- 禁区与红线 → Permission deny / ask  
- 验收与质量门 → Hooks、测试、CI  
- 重复流程 → Skills / Commands  

如果 Spec 只躺在 `docs/` 里从未被 Agent 读到，它就还不是 SDD，只是传统文档。  
**「想」的产物必须成为「做」的输入和闸门，关系才算接通。**

---

## 9. 常见错配：有 Spec 无 Harness / 有工具无方法论

我自己和周围人踩过的：

- Spec 写了三页，Permission 全开，生产配置被改  
- Hooks 配得很炫，却不知道要交付什么，AI 高效地做错题  
- Skills 装了二十个，没有 CLAUDE.md，项目约定全靠嘴说  
- 七层工具都试过，没有主链，场景一切换就重学  
- 文档链停在技术方案，实施指引空着，开工会变成现场发明流程  

错配的解药通常不是再学一个工具，是**补上缺失的那一侧关系**。
