上一篇把 Claude Code 放回「工具层」里看清楚了。这一篇换个动作：打开一个仓库，别急着读业务代码，先扫一眼和 AI 协作有关的那些文件——它们往往比 `src/` 更能说明这个项目「打算怎么跟人 + AI 一起干活」。

课前材料里有一张七层工具图。我后来发现，它不只是选型用的，**读目录时也是一张很好用的滤镜**：先认层，再认路径，就不容易被一堆 `.claude`、`spec`、`mcp` 名字搞晕。


## 1. 这一篇要回答什么

我想搞清楚一件小事：  
**面对一个陌生项目，AI 相关的「表面结构」该怎么读，才不会一上来就陷进实现细节。**

不是背路径清单，是建立一种肌肉反应——看到某个文件，心里立刻知道它在管哪一层事。后面拆主链路、拆模块，都站在这张地图上。

---

## 2. 先看层次，再看目录

很多仓库打开第一眼就很吵：根目录堆着 `CLAUDE.md`、`.claude/`、`.cursor/`、`specs/`、`openspec/`、`mcp.json`……像装修没做完的工地。

噪音的根源通常不是文件多，是**缺少分类锚点**。七层从底到顶大概是：

模型 → 工具 → 配置与约束 → 协作机制 → 协议与生态 → 工作流 → 方法论

目录不会按这七层整齐摆放，但几乎每个 AI 相关文件都能掉进其中一层。  
我自己的习惯是：先问「这是约束、能力、协议，还是工作流产物？」再决定要不要深读。位置对了，重要性也就大概对了。

---

## 3. 模型层 / 工具层 / 配置与约束层分别长什么样

这三层在磁盘上的「长相」差很多。

**模型层**几乎不占项目目录。模型在云端或本机服务里，仓库顶多留下环境变量、provider 配置、一句「我们用 Claude」。看见 `.env.example` 里的 API key 占位，别把它当成架构——那只是原料入口。

**工具层**是你每天真正摸到的东西：Claude Code、Cursor、Codex CLI……它们本身不「长」在业务仓库里，但会在仓库里留下偏好文件。根目录有没有 `CLAUDE.md`，往往比有没有某个框架目录，更能说明团队是不是认真在用 CLI Agent。

**配置与约束层**才是仓库里的主角之一。项目说明、权限、钩子，都在这里。没有这一层，AI 只能按「通用最佳实践」瞎猜；有了这一层，它才有机会变成「懂这个仓库的协作者」。企业级项目里，这一层的价值经常被低估——大家忙着追新模型，却忘了规则文件才是工程化的地基。

---

## 4. 项目里的「说明书」：CLAUDE.md、AGENTS.md

我把 `CLAUDE.md` 当成项目给 AI 看的门牌。

Claude Code 启动时会读它，作用接近前置的 system 上下文。Codex 一侧常见 `AGENTS.md`，Cursor 一侧常见规则文件——名字不同，意图一样：**别每次对话从零解释这个项目是谁。**

一份还能用的说明书，通常会慢慢长出这几块：

- 项目是干什么的、技术栈、目录怎么切
- 怎么 dev / test / build / lint（省得模型猜命令）
- 代码约定：命名、错误处理、测试要求
- 禁区：哪些目录别动、哪些命令先问、哪些绝对不能跑

我越来越相信一句话：**CLAUDE.md 是用出来的，不是第一天想完美的。**  
协作里每发现一次「这条规则它应该知道」，就加一行。半年后，它常常变成仓库里对 AI 最值钱的文档——有时对人读也意外地好用。

---

## 5. 能力封装入口：Skills、Slash Commands、Subagents

说明书解决「你是谁」；Skills 一类东西解决「你会反复做的那几件事」。

常见落点大致是：

| 东西 | 我常去看的位置 | 它在说什么 |
| --- | --- | --- |
| Skills | `.claude/skills/` 或 `~/.claude/skills/` | 可复用能力；合适场景下可被自动选用 |
| Slash Commands | `.claude/commands/` | 手动触发的短流程，如 `/review` |
| Subagents | `.claude/agents/` | 隔离上下文的专职小弟 |

Skills 和 Slash Commands 很像个人/团队的复利账户：代码审查、PR 描述、排障套路、脚手架……封装一次，下次少讲半小时。  
Subagents 则是另一类问题的解法——主对话被几万行代码污染时，把脏活扔进隔离上下文，只收回总结。

不过我也见过反面：任务明明很小，还硬上 Subagents，节奏被拆碎。  
**上下文不挤的时候，主对话往往更干净。** 目录里有 `agents/` 不代表处处都该用。

---

## 6. 协作与协议相关目录（MCP、hooks、plan 产物等）

再往外一圈，是「怎么连外部世界」和「怎么在动手前后拦一拦」。

**MCP** 把工具生态接成可插拔的口子——有人说像 AI 编程的 USB-C。仓库里可能看到 MCP 配置、本地 server 说明、或文档里一串可用工具。看见它，我会想：这个项目希望 Agent 不只写代码，还要碰 GitHub、数据库、内部系统吗？

**Permission / Hooks** 多半藏在 `.claude/settings.json`（以及用户级 `~/.claude/settings.json`）里：

- Permission：事前 allow / ask / deny
- Hooks：PreToolUse / PostToolUse，改完跑 lint、跑测试、拦危险命令

**Plan** 有时是模式开关，有时会留下规划草稿或会话产物。重要的不是文件名有多标准，而是团队有没有「先看计划再动手」的习惯痕迹。

读到这一层，我关心的不是配置语法，而是姿态：  
**他们敢把多大自主权交给 AI，又在哪些地方留了人闸。**

---

## 7. 工作流与方法论相关目录（spec、plan、constitution…）

再往上，目录开始像「想法被写成可执行物」。

不同工具命名不一样，常见气味包括：

- Spec-Kit 一路：`spec.md` → `plan.md` → `tasks.md`，再进实现
- OpenSpec / delta spec：不一定写整本圣经，只写「这次改什么、不碰什么」
- 有的仓库还有 constitution、ADR、设计备忘——给人看的决策，有时也会被 AI 当约束读

这一层对应方法论：SDD 把「想」外化，Harness 相关文件把「做」卡住。  
目录里若几乎只有代码、没有任何规格或计划痕迹，不一定落后——也可能是轻量手工：方案在人脑子里，任务切得很碎，磁盘上只留 `CLAUDE.md` 和几个 Skill。  
**有没有 `specs/` 文件夹，不等于有没有 SDD；有文件夹，也不等于真的在用。** 要看内容新旧，以及是否还在被引用。

---

## 8. 读陌生仓库时的目录阅读顺序

我现在大致按这个顺序扫，尽量十分钟内建立图像：

1. **根目录门牌**：`README`、`CLAUDE.md` / `AGENTS.md` / 规则文件  
2. **工具痕迹**：`.claude/`、`.cursor/`、MCP 相关配置  
3. **约束与反馈**：settings 里的 permission、hooks；有没有 CI 里的 `claude -p`  
4. **规格与计划**：`spec*`、`openspec`、`plans`、ADR  
5. **能力沉淀**：skills、commands、agents  
6. **这才进业务**：`src/`、`apps/`、`packages/`……

顺序故意和「先读核心业务代码」相反。  
因为 Claude Code 这类工具真正改变的是协作面；业务代码永远在，但「AI 从哪被约束、从哪被加速」写在上面那些薄薄一层里。先读它们，后面进 `src/` 时，你会带着「禁区、约定、验收门」去看，而不是两眼一抹黑。

---

## 9. 常见历史包袱与名存实亡目录

地图也要标坟。

- **空的 `.claude/skills/`**：某次分享会建的，再也没人维护  
- **两份打架的说明书**：`CLAUDE.md` 和 README 对启动命令说法不一致——以哪份为准，本身就是风险  
- **复制来的 hooks**：跑着早已删掉的测试脚本，只会制造噪音  
- **spec 目录停在半年前**：SDD 工具引进过，流程没留下  
- **个人全局 Skills 被误当成项目约定**：作者本机很顺，克隆仓库的人什么都没有

遇到这些，我不当教程缺陷，当考古现场：说明团队在哪一层试过、又在哪一层放弃了。  
名存实亡本身也是信息——**别把目录当现状，把「最后一次认真编辑」当现状。**
