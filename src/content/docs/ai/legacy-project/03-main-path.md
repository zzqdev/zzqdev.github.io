**一次真实协作，从模糊想法到可验收结果，中间到底经过哪几站？**

## 1. 这一篇要回答什么

我想留下一张「走路图」，不是命令手册。

读完之后，面对一个需求，我能大致判断：该走哪条路径、每一步产出什么、人盯哪、AI 扛哪。细节可以后补；**主链丢了，工具再多也只是加速迷路。**

---

## 2. 工作流变了什么：产出物、协作、反馈

很多人以为 AI 编程只改了「写代码那一段」。真正变的是整条工程链路。

**产出物**不止给人看。Spec、Plan、CLAUDE.md、Skills、Hooks——第二个读者是 AI。Bun 那次大规模迁移里，翻译规则写进给 Agent 执行的约束文件，而不是只塞进 Wiki，就是这个味道。

**协作**不再是人对人交接。需求、设计、实现、测试，人和 AI 常常同时在场：人拍板方向与风险，AI 扛执行量。分工判断本身成了核心能力——什么交给它、什么必须自己留。

**反馈**被工程化了。Permission 事前拦，Hooks 事后查，测试套件当门禁。反馈周期从「等测试同学发现」压到秒和分钟。你不再只是代码最后一道防线，更像在设计这条防线。

看不清这三变，就只会让 AI 替你少打几行字；看清了，才谈得上主链路。

---

## 3. 主轴：先想清楚，再约束着做

我把主轴压成八个字：**先想清楚，再约束着做。**

- **想清楚** → SDD：把意图写成可审查、可共享、可执行的 Spec  
- **约束着做** → Harness：规则、能力封装、权限、钩子、先规划再动手  

两者互补：只有 Spec，执行仍可能跑偏；只有挽具，方向可能从一开始就歪。  
主链不是某个工具的命令序列，是这条「想 → 做 → 验」的闭环在不同重量级下的展开。

---

## 4. 路径 A：Spec-Kit 自动化模式主链路

Spec-Kit 把「想」外化得最完整，典型节奏是：

`/specify` → `/plan` → `/tasks` → `/implement`

人的重心在写清 Spec、检查 Plan、最后 Review；中间拆任务和执行，工具倾向交给 AI。适合中等复杂度、想快速试错、或还在练 SDD 手感的时候。

我也吃过它的代价：两轮推断叠加——AI 拆任务一轮、执行再一轮——误差会相乘。Spec 写得再漂亮，也装不下你脑子里全部工程直觉。  
所以这条路径我当「脚手架」，不当「放弃判断的借口」。

---

## 5. 路径 B：OpenSpec / delta spec 主链路

OpenSpec 更像「人握方向盘」。常见姿态是：人写 Spec / Plan，人拆任务，AI 一次只吃一小块，块块 Review。

对老项目特别顺的是 **delta spec**：不写整本圣经，只写这次改什么、改成什么样、为什么改、不破坏什么。改造、开源 PR、系统性修一类 bug，往往比硬套完整 Spec 流程更贴地。

全局视角留在人手里，AI 只在局部执行——这是这条路径最值钱的分工。

---

## 6. 路径 C：轻量手工模式（CLAUDE.md + Skill + 提示词）

第三条路径几乎不依赖 SDD 专用工具。方案在脑子里（或草稿纸上）跑通，任务切到「一次能写完、一次能看完」，一段一段交给 AI，立刻 Review。

磁盘上常常只有：`CLAUDE.md` + 几个 Skill。没有 Subagents 盛宴，没有自动化 Spec 流水线。

它适合：熟悉的技术栈、想得清楚的业务、关键路径、在意可维护性的增量。  
不太适合：完全陌生的领域、还在探索的产品验证、规模大到脑子装不下的拆分。

我一度以为「让 AI 多做决策更快」。后来发现，**决策做错再收回来，通常比人先想透再让它执行更慢。** 轻量模式逼你每天练「想清楚」——这恰恰是不该外包的能力。

---

## 7. 一次完整循环：Spec → Plan → 执行 → Review → 验证

不管走哪条路径，完整一圈长得差不多：

1. **Spec**：做什么、不做什么、怎么算完  
2. **Plan**：怎么做、动哪些面、风险在哪  
3. **执行**：按任务或小段改代码  
4. **Review**：人对产出拍板，不只是「能跑」  
5. **验证**：测试、门禁、必要时故障注入  

路径差异主要在：Spec/Plan 写到多细、谁来拆任务、任务粒度多大、Review 卡在哪一层。  
主链的灵魂是**可回到上一站**——发现方向错了，退回 Spec；发现拆错了，退回任务边界；而不是在错误实现上继续 vibe。

---

## 8. Plan Mode、Permission、Hooks 在链路上的位置

这三样不是装饰，是主链上的闸：

| 机制 | 卡在哪 | 像什么 |
| --- | --- | --- |
| Plan Mode | 执行前 | 先出示路线，再允许动工 |
| Permission | 工具调用前 | 红线与可自由活动区 |
| Hooks | 调用前/后 | 自动 lint、测试、拦危险命令 |

熟悉的小改动可以少开闸，效率优先。  
改核心、改配置、陌生区域、第一次摸某类任务——默认多开几道。  
闸不是越多越好，是**出错代价大的地方，闸要在。**

---

## 9. 卡住时怎么回到主链，而不是 vibe coding

卡住时的典型坏味道：改 prompt、再生成、再看着不对、再改 prompt……一天结束，仓库更乱，意图更糊。

我给自己的急救顺序很土：

1. 停手。问：我现在卡在「想不清」还是「做不稳」？  
2. 想不清 → 回到 Spec / 口头重述验收标准，写下来再继续  
3. 做不稳 → 缩小任务粒度，或打开 Plan Mode / Permission，先看它打算干什么  
4. 已经改脏 → 用 git 回到已知好点，带着更清楚的 Spec 重走，而不是在脏状态上补丁叠补丁  

Vibe 不是罪恶；**把 vibe 当成唯一工作方式，才是主链断裂。**
